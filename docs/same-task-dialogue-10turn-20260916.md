# 同一 task 十輪對話：UI/UX 成品與成本（2026-09-16）

## 實際情境

同一個照護者用藥規劃原型，使用者連續十次提出相近的後續修改；不是十個無關題目，也不是十個新的 Codex task。兩組分別持有自己的 app-server thread，使用 `gpt-5.6-sol`、low reasoning、相同初始專案與相同使用者追問。對照組收到簡短執行要求；UAP 組在初始化專案後，每輪收到 UAP execution packet。此實驗**沒有**呼叫完整 Orchestrator。

追問脈絡：① 初版響應式無障礙用藥頁面 → ② 狀態篩選及衝突提示 → ③ 新增用藥對話框 → ④ 表單錯誤與焦點 → ⑤ 重複用藥警告 → ⑥ 用藥搜尋 → ⑦ 無結果與朗讀提示 → ⑧ 本機保存及復原 → ⑨ 列印版 → ⑩ 醫療安全文案與回歸整理。完整逐字 prompt 在 `scripts/same_task_quality.py` 的 `GOALS`，且兩組相同；沒有在輪次之間換題目。

## 品質檢查與實物

`scripts/same_task_quality.py` 在每輪重新檢查之前所有要求，搭配現有基礎 UI/UX 驗收及 Node.js 的 inline JavaScript 語法檢查；任何缺漏都會逐輪列出。最終原型的搜尋、空結果、重複提醒、本機存取、列印規則及安全文案另經原始碼抽查。每輪 HTML 快照在 `.benchmark-same-task-coherent10-sol-20260916-r1/snapshots/{baseline,uap}/`，最終成品分別在該工作目錄的 `{baseline,uap}/prototype.html`；完整 provider 用量與驗收結果在同目錄 `report.json`。

這些驗收**不等於**瀏覽器互動測試、無障礙工具測試或真人設計品質評分。嘗試以 Windows UI 開啟原型進行視覺驗證時，Computer Use 的應用程式核准逾時，所以沒有宣稱視覺／操作品質等價。醫療內容只是虛構 UI 測試資料，不提供臨床建議。

## 限制與下一步

- 只有一組成對樣本，順序是 baseline 後 UAP，沒有反向順序或不同專案的重複試驗，差異可能受 provider 隨機性影響。
- UAP 組同時改變專案初始化與 prompt 包裝，不能從本次數據分離單一機制的貢獻。
- 品質檢查偏重結構、存在性與語法；下一版需要真正瀏覽器操作、鍵盤及視覺盲評。
- `--max-tokens-per-arm` 只在下一輪開始前檢查；最後一輪可以越過門檻。此次 baseline 最終為 2,198,782，高於設定的 2,000,000 啟動門檻。
- 20 輪與跨新 task 重用尚未執行。值得先反向順序複測十輪，再擴成二十輪，避免只把一個偶然結果放大。
