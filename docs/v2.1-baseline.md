## Installation baseline

The documented public path is still an editable checkout install (`pip install -e .`). The
project has standard setuptools metadata and an `agentctl` entry point, so a Git URL can build
the Python code, but runtime resources are not declared as package data. No clean Git-install
or source-checkout-independent guarantee exists at this baseline.

## Package-data and checkout dependency

Runtime code defines `PACKAGE_ROOT` as two parents above `src/adaptive_agent/runtime.py` and
loads `config/`, `templates/`, and `dashboard/` from that repository root. `pyproject.toml`
only discovers Python packages and does not include those directories in wheel data. As a
result, models, profiles, templates, and dashboard assets can depend on a nearby source
checkout even if the console script itself installs successfully.

## Known V2.0 limitations relevant to V2.1

- Public onboarding recommends editable installation rather than a Git URL.
- README, `AI-BOOTSTRAP.md`, and `agent-platform.json` do not yet share a direct-install contract.
- No second real provider adapter is implemented.
- Provider capabilities are visible but are not yet a hard routing constraint with rejection reasons.
- Execution mode does not distinguish agentic local, API reasoning, local model, and mock backends.
- Provider preference is not demonstrated to fall back on hard capability incompatibility.
- There is no bounded generic `provider-test` command or offline cross-provider demo.
- Dashboard provider data lacks the V2.1 execution-mode and compact bootstrap-health presentation.
- Version metadata is `2.0.0` and no changelog exists.
- The source tree is healthy, but installed-distribution resource loading is untested.

This document is evidence for the starting point only. V2.1 validation belongs in separate
release and bootstrap validation documents.
