## 比較方式

- 兩組相同初始來源、相同 task、同一份未修改的外部驗收。
- 兩組都取得 prepare 的原始碼摘要及相同正確 allowlist 命令；主要差異
  是成功操作記錄與隨之增加的使用提醒，不再混入「有／無來源摘要」差異。
- 前置階段在兩個 fixture 都執行一次既有測試，使副作用一致；只有記憶組
  保存成功證據。冷組在此指 AI 沒有成功紀錄，不代表電腦完全未執行過測試。
- 前置測試／保存耗時：冷組 1.765 秒、記憶組 2.157 秒。兩組前置 AI
  呼叫均為零；記憶組 prepare 256.45 ms。沒有測量首次 AI 探索命令成本。
- 此模式報表的 initial_index_ms=0.002 是跳過舊初始化分支的時間，不能
  視為索引建立成本。真正 prepare 成本列在 warm_prepare_ms。
- 使用本 checkout 的 PYTHONPATH，兩組都收到以 `python -m adaptive_agent.cli`
  代替全域 agentctl 的相同說明；沒有更動全域安裝。

## 觀察與仍未知之處

冷組的命令皆零退出，沒有保存到失敗線索。記憶組包含一次帶
permission/test_failure 線索但外層退出 0 的複合呼叫，以及一次带
missing_dependency 線索、退出 1 的驗證呼叫。前者也說明不能只靠外層
exit code 判斷複合命令裡的每個檢查是否成功。

執行後本機設定同一 PYTHONPATH，可以在 fixture 目錄成功啟動 CLI help。
Provider 程式碼會繼承環境，但這不證明 AI 內部每個 shell 都使用相同環境。
保留的紀錄只有去識別化線索，無法確認缺少哪個模組或是哪個操作觸發權限問題。
SQLite 成功計數仍為 1；不能憑這個數字證明任務完全沒有嘗試過記憶路徑，
因為環境指紋改變可能重設計數。

下一步應先離線驗證「已知命令可以在實際執行邊界直接可靠使用」，以及
複合檢查能否誠實回報失敗，再考慮新的付費試验。不能再把更多記憶提示
視為天然最佳化。本輪保留失敗結果，不調驗收、不重跑挑數字。

實際任務的長期攤提，也不證明跨不同領域的模型效果。
