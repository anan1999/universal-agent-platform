# SOL 配對工具額度 Benchmark（2026-09-16 R2）

## 結論

在這個單一 full-stack 任務上，把提示中的 provider 工具額度從 8 收緊到 6，並維持相同的 bounded-execution 指令，6 組配對總 Token 從 501,186 降到 433,108，減少 68,078（13.58%）。12 個成品全部一次通過同一份凍結外部驗收，且 12 筆 Token usage 都是完整實測值。

這是值得繼續驗證的訊號，但不是「hard cap 6 已證明有效」：所有執行實際只用了 1–3 次工具呼叫，沒有碰到 6 或 8 的硬上限。較合理的解讀是，較緊的額度數字作為執行提示，可能讓 SOL 更傾向批次處理與提早收斂；結果仍包含模型隨機變異。

## 方法

- 模型固定為 `gpt-5.6-sol`，reasoning 固定為 `low`。
- 每組從完全相同的乾淨 fixture 建立兩份專案。
- 唯一 treatment 差異為提示及 execution budget 中的工具額度：8 對 6。
- 執行順序每組交錯，降低先後順序偏差。
- 不限制對話輪數；以凍結的功能驗收通過為完成條件。
- 若需要修正，會在原成品上繼續，所有嘗試成本都必須累計。
- 精確 Token 來自 Codex app-server 的最終 usage 通知；不接受估算或 0 值替代。
- 安全上限為每 arm 500,000 tokens／900 秒。

任務是新增月報 API 與 React dashboard 顯示，同時保留既有 expense 行為。驗收合約 SHA-256：`55714f5ba8ed4d949714be0c673a41676466ad09be04376e6a2c9f750cca15fb`。

## 與 `4aae8fc` 的關係

舊結果報告的總降幅為 13.93%；這次在修正精確 usage 路徑、交錯順序及排除不完整配對後得到 13.58%，方向與幅度相近。不過本次揭露了逐組波動（+25.48% 到 −53.23%），也確認硬上限從未真正綁住執行。因此舊方向有重現，但因果機制應描述為「較緊的執行預算提示」，不能說是「cap 6 截斷工具呼叫」已獲證明。

## 已修正的量測問題

第一次 R1 嘗試把 `codex_live_usage` 放在錯誤的巢狀欄位，導致一筆已完成成品缺少正常收尾資料。R1 已保留為不可變的失敗證據，未納入結果。修正版將 live-usage 設在 task metadata，並把不完整配對列為 `excluded`，不允許 0 tokens 被誤算成節省。

## 下一個必要實驗

以更複雜、通常需要超過 6 次工具窗口且可能需要返工的任務做 paired benchmark，並把「提示文字」與「硬 cap」拆成 2×2 實驗。這樣才能分辨節省來自預算錨定、批次工作指令，還是硬性中止，並量到品質不足所造成的後續修正成本。
