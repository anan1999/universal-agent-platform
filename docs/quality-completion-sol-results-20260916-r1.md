# SOL 品質收斂 Benchmark（2026-09-16，R1）

## 結論

在這一次固定使用 `gpt-5.6-sol` 的三領域實測中，Baseline 與 UAP 最後都通過相同的結構合約。
UAP 總 observed tokens 為 825,047，Baseline 為 1,008,008；UAP 少 182,961（18.15%）。

這不能解讀成「UAP 穩定省 18.15%」。樣本只有每領域一條三需求序列，而且總差距高度受一次
Baseline 品質失敗影響。平面設計反而是 UAP 多用 12.44%。目前可支持的結論是：UAP 有機會
藉由避免完整返工降低品質達標總成本，但初始化與額外上下文在部分任務會吃掉節省。

## 方法

- 模型：Baseline 與 UAP 全部固定為 `gpt-5.6-sol`，receipt 模型不一致即失敗。
- 領域：UI/UX、平面設計、3D 設計；每個領域是一個全新專案及三個累積需求。
- 終止條件：不是固定對話輪數。每個需求持續修正，直到獨立驗收合約通過；400,000 tokens／
  900 秒只是每臂每需求的安全上限。
- 隔離：兩臂各自保留自己的作品，不借用另一臂的成功 checkpoint。
- 記帳：每次 provider 呼叫先寫入 SQLite；失敗、修復與成功成本全部累加。全部 19 次呼叫都有
  `token_source=measured` 且 `usage_complete=true`。
- 順序：需求間交替先跑的 arm，降低固定先後順序偏差。

## 結果

| 領域 | Baseline attempts | UAP attempts | Baseline tokens | UAP tokens | UAP 差異 |
| --- | ---: | ---: | ---: | ---: | ---: |
| UI/UX | 4 | 3 | 508,379 | 308,647 | -199,732（-39.29%） |
| 平面設計 | 3 | 3 | 247,074 | 277,821 | +30,747（+12.44%） |
| 3D 設計 | 3 | 3 | 252,555 | 238,579 | -13,976（-5.53%） |
| **全部** | **10** | **9** | **1,008,008** | **825,047** | **-182,961（-18.15%）** |

所有 18 個 arm-task 最終結果均為 `contract_passed`。唯一的額外 attempt 出現在 UI/UX 第三題：
Baseline 首次呼叫消耗 169,135 tokens，但缺少 Escape 鍵行為；第二次再消耗 124,433 tokens 才通過。
UAP 該題一次通過，消耗 94,073 tokens。失敗呼叫本身相當於總差距的 92.44%，因此不能把整體
18.15% 當作穩定的上下文壓縮收益。

## Token 結構

| 指標 | Baseline | UAP | 差異 |
| --- | ---: | ---: | ---: |
| Observed tokens | 1,008,008 | 825,047 | -182,961 |
| Cached input | 739,584 | 606,848 | -132,736 |
| Non-cached input（推算） | 241,477 | 193,963 | -47,514 |
| Output tokens | 26,947 | 24,236 | -2,711 |

差距主要在輸入側，不是把最終文字回答壓短。另一方面，平面設計的 UAP 並未受益，說明目前
reuse context 的選擇仍不夠穩定，不能對所有設計任務一律注入相同的專案情報。

## 品質邊界

本輪驗收的是可重複執行的 HTML/SVG/OBJ 結構合約，包括指定互動、可存取性標記、圖層、材質、
幾何群組與 face index。它沒有做盲測視覺評審，因此只能說兩邊都達到相同的機器可驗規格，不能
宣稱主觀美感、實際可用性或視覺品質等價。若加入 AI／人工視覺評審，其評審與再修成本也必須
另外完整記帳。

## 下一個最有價值的修正

先不要繼續追求全域 Token 壓縮。應把 UAP 的 reuse 注入改成「只有預估可避免搜尋或返工時才
載入」，並以平面設計第二題作負向回歸案例。下一輪至少重複不同 seed／題序三次，觀察 UI/UX
的返工避免效果是否可重現，才能區分真正的機制效果與單次 SOL 隨機性。
